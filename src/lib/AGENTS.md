- Navigation rules live in src/lib/nav-rules.ts; pro status comes only from is_professional, fail-closed on error; offline reuses the account's last server check (src/lib/pro-status.ts, 7 days max). Why: no UI escalation from a membership label; RLS stays the security boundary.
- Carnet de vie du chien : construit côté client depuis les tables existantes (participation_dogs, dog_goals, dog_observations) via src/lib/dog-timeline.ts, sans table dédiée ni données humaines. Pourquoi : aucune donnée dupliquée, RLS inchangée.
- Libellé de rôle de l'accueil : dérivé uniquement de is_bureau/is_professional (memberRoleLabel), jamais des tâches. Pourquoi : une tâche ne change pas l'identité.
- Hors réseau : src/lib/offline.ts et public/offline.* conservent uniquement pass et demandes temporaires par compte ; ne jamais afficher un tampon local comme confirmé. award_manual_stamp reste la validation serveur. Ne pas rejouer automatiquement les demandes d'un autre jour (manual_key dépend de la date serveur) : elles passent par submit_offline_stamp_mediation (Bureau notifié, aucun tampon créé). Aucune page n'émet X-LVDC-Public-Cache : aucun HTML mis en cache, la navigation hors réseau retombe sur /offline.html ; lvdc.public.pros ne contient que des champs déjà publiés. Service worker généré et enregistré uniquement en production, jamais en aperçu.
- Profils : e-mail/téléphone retirés des droits SELECT par colonne ; lire avec PROFILE_COLUMNS et withContacts (RPC profile_contacts, soi-même ou Bureau). Jamais select("*") sur profiles. Pourquoi : aucune fuite de coordonnées par l'API.
- Pass Terrain : identification par resolve_member_from_qr (code complet ou court 8 car., src/lib/pass-code.ts), pros sans lecture de loyalty_cards ; profil créé par trigger auth.users à partir des métadonnées d'inscription. Pourquoi : statut PENDING imposé et données d'inscription conservées.
- Finances : trois circuits distincts, jamais additionnés — accounting = recettes/répartitions et reversements pro (professional_paid_at) ; reimbursements = demandes des membres (PENDING→APPROVED/REJECTED, APPROVED→PAID/REJECTED, payé/refusé figés, jamais sur sa propre demande, transitions et audit dans guard_reimbursement) ; finance_entries = suivi opérationnel/export, sans accès personnel (notes internes). Droits sensibles = bureau_has_permission (Bureau ET permission : finance.view_global/create/update, reimbursements.validate/mark_paid, members.validate), miroir client useSensitiveRights. Pourquoi : Bureau ≠ accès financier illimité.
- Console Bureau : /admin est l'entrée canonique (ancien /admin/cockpit redirige) ; onglets BureauConsoleTabs vers /admin/validation, /finance, /admin/suivi-financier. Adhésions : file unique PendingMembersQueue, décision uniquement via decide_membership (verrou, journal, notification) ; guard_profile_membership refuse toute autre sortie de PENDING. Pourquoi : un seul écran, une seule file, décisions tracées.
- Annuaire : guichet unique (onglets Réseau/Pros/Partenaires/Adhérents/Mairies) via src/components/DirectoryTabs.tsx ; une seule entrée de menu. Pourquoi : regrouper sans casser les pages existantes.
- Notifications de collaboration (commentaires, tâches, projets, propositions, guides, aides) : émises uniquement par déclencheurs via notify_member/notify_bureau_members (anti-doublon, préférences, droits de lecture vérifiés) ; l'interface n'insère jamais de notification. Pourquoi : l'insertion directe est réservée au Bureau par la RLS et échouait en silence pour les membres.
- Gouvernance Bureau (/admin/gouvernance) : agrège propositions, contributions, réservations terrain et demandes d'aide via src/lib/governance.ts, sans table ni copie de statut ; adhésions/tâches/remboursements seulement comptés avec renvoi vers leur file. Pourquoi : pas de seconde file de validation.
- global_search : documents et formulaires limités aux métadonnées, mêmes conditions que leurs politiques RLS ; jamais url, champs ni réponses. Colonnes du premier SELECT aliasées (h_*) car les noms OUT de plpgsql entrent en conflit.
- Registre de gouvernance (governance_records) : comptes rendus AG/Bureau/réunions, lecture et écriture Bureau seul via RLS is_bureau. Pourquoi : suivi complet des réunions sans exposer aux membres.
- Fonctions SECURITY DEFINER : EXECUTE retiré à anon sauf list_public_pros, get_public_pro_page, get_public_home, list_public_activities, list_public_blog_posts, submit_form_response ; toute nouvelle fonction doit révoquer anon. Pourquoi : aucun oracle anonyme.
- Formulaires : audience PUBLIC (libre) / INTERNE (adhésion ACTIVE via is_active_member), appliquée à la RLS et à submit_form_response. Pourquoi : un compte en attente ne lit ni ne soumet un formulaire réservé.
- Lieux : champ lieu libre + adresse facultative ; Maps/copie/météo Open-Meteo via src/components/PlaceInfo.tsx (côté navigateur, sans clé). Mairies identifiées via entity_mairies (écriture Bureau) et linked_mairies. Dates de gouvernance en heure de Paris (src/lib/places.ts).
